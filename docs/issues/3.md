# Issue #3 — Update `include_tables` on a live capture session

**GitHub:** [ce-stream/ce-stream#3](https://github.com/ce-stream/ce-stream/issues/3)  
**Label:** Feature  
**Status:** **Implemented** (pending merge + annotated tag **v0.3.0**). Close with `Fixes #3` on the PR.

> **Resolution:** `IncludeList` handle on `MysqlBinlogSource`. Dump thread holds an `Arc`; each GTID snapshots the list for that envelope. Ship as **v0.3.0**.

## Problem summary

`include_tables` was copied into a `HashSet` when `run` / `run_transactions` started. Embedders that add or drop watched tables had to stop the dump client and reconnect (new GTID handshake, gap in the ordered reader).

## Behavior

- `source.include.clone()` / `include_handle()` is a cloneable `Arc`.
- `insert` / `remove` / `replace` take effect at the **next GTID**, never mid-envelope.
- **Best-effort, no ack.** The next transaction after the following GTID uses the new list.
- Newly included tables: later commits deliver their row events.
- Removed tables: later commits omit their row events. Fully filtered commits are still delivered so the GTID watermark advances.
- Empty `include_tables` at start: all tables (v0.2.0). After start, removing the last table or `replace([])` means no row events.
- DDL Query events are **not** filtered by the include list (v0.2.0; no DDL table classifier).

## Non-goals (this issue)

- Schema identity / mapping versions inside ce-stream
- Changing `delivery_unit` or commit-boundary checkpointing
- CLI live-reload of `include_tables` (restart the process)
