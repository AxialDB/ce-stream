# Issue #13 — MySQL: a DDL statement on its own is never delivered

**GitHub:** [AxialDB/ce-stream#13](https://github.com/AxialDB/ce-stream/issues/13)
**Label:** bug
**Status:** **Released** in **v0.4.3** ([#14](https://github.com/AxialDB/ce-stream/pull/14)).

> **Resolution:** a transaction ends at its `Xid` event, at its `COMMIT` query, or, for a statement that is a transaction by itself, at its one `Query` event. Every GTID the server sends is delivered or, for the two shapes that are not supported, passed over without stopping the stream.

The **Problem summary** below is the defect as reported. It is not current runtime behavior.

## Problem summary

The MySQL source delivered a transaction only when it read an `Xid` event. MySQL writes a plain DDL statement as one `Gtid` event and one `Query` event, with no `Xid` after it. So:

- **The DDL was never delivered.** The statement went into the transaction buffer, nothing flushed it, and the next `Gtid` event cleared the buffer. A consumer that relies on `ddl` to learn that a table it follows was altered, truncated, or dropped never heard of it.
- **Its GTID never entered the executed set.** `gtid_set_after` and the checkpoint had a hole at every DDL statement.

Found with the same cause:

- A transaction on a table without transactions (MyISAM) ends with a `COMMIT` query and no `Xid`. It was never delivered either.
- A statement that is neither DDL nor in a transaction (`GRANT`, `ANALYZE TABLE`) left the same hole.
- `is_ddl_query` tested the start of the statement text. A statement with a comment in front (`/* ApplicationName=... */ ALTER TABLE ...`) was logged as "ignored non-DDL query".

The earlier DDL tests fed `Query` + rows + `Xid` in one transaction without a `BEGIN`, a shape the server writes for no plain DDL statement.

Found while the fix was checked against a server, with another cause, and fixed in the same change:

- **`gtid_set_after` left out commits that waited in the queue.** The reader built it from the consumer's executed set, which moves only when a commit is taken from the queue. With DDL delivered, a start from a checkpoint reads several commits before the first is taken, and the second arrived with a set that did not name the first. The same could happen before with any two row transactions close together. The checkpoint was not affected.

## Behavior

The sequences are those of a MySQL 9.7.2 binlog (`binlog_format=ROW`, `gtid_mode=ON`), read with `mysqlbinlog`:

| Statement | Events after the `Gtid` | Delivered |
|-----------|-------------------------|-----------|
| InnoDB `INSERT` | `Query BEGIN`, `Table_map`, `Write_rows`, `Xid` | at the `Xid` |
| MyISAM `INSERT` | `Query BEGIN`, `Table_map`, `Write_rows`, `Query COMMIT` | at the `COMMIT` |
| `CREATE TABLE ... SELECT` | `Query BEGIN`, `Query CREATE TABLE ... START TRANSACTION`, `Table_map`, `Write_rows`, `Xid` | at the `Xid`, DDL and rows together |
| `CREATE TABLE`, `ALTER TABLE`, `TRUNCATE TABLE`, `DROP TABLE`, `CREATE` / `DROP DATABASE`, `CREATE` / `DROP USER` | one `Query` | at that event, with `ddl` set and no events |
| `GRANT`, `ANALYZE TABLE` | one `Query` | at that event, as a commit without events |

- **In brackets or not.** A `BEGIN` query (or `XA START`) opens a transaction whose end comes later. Without one, the first statement after a `Gtid` is the whole transaction. A DDL statement whose text ends with `START TRANSACTION` opens a transaction even without a `BEGIN` in front.
- **Statements inside a transaction** (`SAVEPOINT`, `ROLLBACK TO`, `XA END`) do not end it.
- **A comment in front of a statement** is skipped when its verb is read; what is inside `/*!50003 ... */` is the statement. The `query` text is delivered as the server logged it, comment included.
- **`gtid_set_after`** is the set the reader started from, every transaction it has passed on, and the commit itself. It does not depend on how far the consumer is. A transaction that is not delivered is in no set.
- **A transaction still pending at the next `Gtid`** had no end the adapter knows. It is not delivered, as before, and a warning names its GTID and its buffered row count.

## Non-goals (this issue)

- **XA transactions.** The rows between `XA START` and `XA PREPARE` are not delivered, as before. Their `XA COMMIT` or `XA ROLLBACK` is a statement of its own and arrives as a commit without events.
- **A transaction the binlog ends with `ROLLBACK`** (a rolled-back transaction that touched a table without transactions). Not delivered, as before.
- Classifying DDL. The adapter passes the statement text on; what it means for a table is the consumer's to decide.

- Not in CI: the CLI against MySQL 9.7.2 (`delivery_unit = "transaction"`, stdout sink), next to a build without the fix reading the same statements. 16 statements in a scratch database, 17 transactions: `CREATE DATABASE`, `CREATE TABLE`, `INSERT`, `ALTER TABLE ... ADD COLUMN`, `UPDATE`, `TRUNCATE TABLE`, `CREATE TABLE ... SELECT`, a MyISAM `CREATE TABLE` and `INSERT`, `ANALYZE TABLE`, `ALTER TABLE ... DROP COLUMN`, `RENAME TABLE`, `DELETE`, `DROP TABLE`, `DROP DATABASE` (two transactions: the server drops the MyISAM table in one of its own).
