# Issue #19 — One contract for every source, and `ce-stream-postgres`

**GitHub:** [AxialDB/ce-stream#19](https://github.com/AxialDB/ce-stream/issues/19)
**Label:** (feature)
**Status:** **Released** in **v0.6.0** ([release notes](../releases/v0.6.0.md)), after its first consumer (AxialDB) built its MySQL, MongoDB and PostgreSQL hosts on it and tested them on its lab.

> **Resolution:** `ce-stream-core` says what every source delivers (`Delivery`), how positions compare (`covers`), how a consumer confirms (`Confirm`), how a seed lines up (`SeedCut`), and what a gate reports (`GateReport`). MySQL and MongoDB moved onto it, and `ce-stream-postgres` is the first source written against it.

The issue on GitHub has the full design. This page has what the build found.

## Where the build differs from the issue

- **A position compares by the end of a commit.** The issue has `covers` as `target.at.lsn <= at.after.lsn`, and a resume that drops a commit "at or below" the checkpoint. A commit record can start exactly where the one before it ended: in a crash loop with 4 writers, 1991 of 6000 commits did. Both rules would lose such a commit. `covers` compares `target.after.lsn <= at.after.lsn`, and a resume drops only a commit that starts below the checkpoint, as the server does (`SnapBuildXactNeedsSkip`). A part's target has no `after` and is covered once a position is past its commit's start.
- **`at` has no `end_lsn`.** The issue has `at = { lsn, end_lsn, xid }`. A part is delivered before its commit's end is known, and every part of a transaction has the same `at`, so `at = { lsn, xid }`. The end is `after.lsn`.
- **A mark's LSN is the same in the stream and from `mark()`.** `pg_logical_emit_message` returns the end of its record, and `pgoutput` sends that LSN.
- **The checkpoint store has two steps.** `save` is atomic and may run on every commit. `sync` makes it survive the machine. The slot moves only to what has been synced, once a second, so a checkpoint is never behind its slot after a power cut. An fsync per commit held the stream to about 4 commits a second on a lab disk; the same run does about 1000 now.

- **MongoDB values follow the contract, with the types beside them.** The issue first left the extended JSON tags in place. A row now has the contract's values in its image, and `types` for what they do not show ([`../values.md`](../values.md#mongodb)). So the stream looks the same on every host, and a consumer that needs a value's true type still has it, which a failed cast relies on. Per row, since types can differ per document. A learned `Schema` for MongoDB, chosen by an option, was considered and left out until someone asks for it: it would add nothing the embedder could use.

## Added after the design review of 2026-11-09

Both are built and unit-tested on the branch, and both have run against servers through the consumer's lab: AxialDB's engine built on this branch by path, on buildcomp, with MySQL 9.7.2 and 8.4 and PostgreSQL 17 and 18.

- **Failover slots and `fork_point`:** planned switchover, unplanned failover through a synchronized slot, unplanned failover with lost changes, capture from a standby that is promoted, and capture from a standby when another is promoted. Five cases on a three-server lab, PostgreSQL 17 and 18, passed 2026-11-12 and again 2026-11-13.
- **MySQL partition ids:** drop, truncate, exchange, reorganize, and `HASH` add and coalesce of partitions under writers, on MySQL 9.7.2 and 8.4, passed 2026-11-12 and 2026-11-13.
- **Purged binlogs** (`purged_missing`, the `HistoryLost` path): a replica that purged, and all servers purged, on a three-server MySQL lab, passed 2026-11-13.
- **XA:** rows at `XA COMMIT`, none at `XA ROLLBACK`, on three MySQL 9.7.2 servers, passed 2026-11-13. A restart of the consumer between `XA PREPARE` and its end, and a planned switchover between them, passed in AxialDB's final release round (2026-11-22).

What was added:

- **MySQL rows carry their partition.** The vendored parser reads the rows event's extra row information instead of skipping it (`parse_rows_event_common_header`, type 1 `PART`, type 0 NDB skipped by its length byte, an unknown type ends the reading), and `ce-stream-mysql` delivers `partition_id` and, on an update, `source_partition_id` as extensions of the row's event. A plain table has neither.
- **Failover slots.** `create_slot(options, slot, failover)` adds `FAILOVER true` to the command; `alter_slot_failover` marks an existing slot before the stream starts; `SlotFigures` adds `failover` and `synced`; the CLI has `failover = true`. A checkpoint on an older timeline than the server's resumes when it is at or before the point where the server's timeline forked from it (`TIMELINE_HISTORY`), and is `Error::Checkpoint` past it; `fork_point` gives an embedder that point, and `server_identity` the server's system identifier and timeline. A server on an older timeline than the checkpoint's is refused as an old primary.

## Added after the design review of 2026-11-10

Built and unit-tested on the branch; the lab run is in the issue.

- **MySQL says when the history is gone.** On resume the source added the server's `gtid_purged` to the set it sent with the dump, so the server never refused and skipped what it had purged. A lab run lost 60 inserts and 60 updates that way with the stream running and no error, once on a replica that had purged while the new primary had not, once with no failover and every server purged. A resume is now `Error::HistoryLost` when the server's `gtid_purged` holds a transaction that is in neither the checkpoint's `gtid` nor its `baseline_gtid`, as PostgreSQL and MongoDB already answer; otherwise the dump is sent the checkpoint's own set. The server's own refusal (error 1236 on purged binary logs) is `HistoryLost` too. A public call answers the same question without starting a stream, for a consumer that chooses among several servers. A checkpoint with no baseline keeps the old handshake, with a warning.

## What the crash loop found

`FileCheckpointStore` wrote in place, so a kill during the write left an empty file and every restart refused it. A save now writes a temporary file and renames it.

## What the lab found about the server

- **An announcement is not a signal of a rewrite.** The server announces a table again after anything that invalidates its cache entry, `VACUUM` and `ANALYZE` included. A repeated `Schema` says only "look again"; the file node and the column's row in `catalog_tables` say what happened.
- **A keepalive comes as soon as the server has passed what the client has confirmed**, not only at half of `wal_sender_timeout`, so a quiet stream learns its position within moments of an unpublished write.
- **The server compiles the query of `catalog_tables` with JIT at every call, so the connection turns JIT off** (`SET jit = off` before the query; found 2026-11-22). The planner counts the function scans inside the query's subqueries (`pg_partition_tree`, `pg_get_publication_tables`) at 500 and 1,000 rows each, which prices the query at over a million, above `jit_above_cost` and the limits for inlining and optimizing. On 17 at its defaults: 574 ms for 15 tables and 571 ms for 207, of which 555 ms compiling; 1.9 ms with JIT off. For one table the price can still pass `jit_above_cost` (55 ms against 0.4 ms). A compiled query is not kept, so a consumer that asks every 30 s paid half a second of one core each time.

| After | File node moves | Column's row moves | `DefinitionChanged` |
|-------|-----------------|--------------------|---------------------|
| `ADD COLUMN` | no | no | yes |
| `VACUUM`, `REINDEX`, `ANALYZE` | no | no | no |
| `VACUUM FULL`, `CLUSTER`, `TRUNCATE` | yes | no | no |
| `ALTER COLUMN ... TYPE` | yes | yes | yes |

The same on 17 and 18. The server announced the table again after each of them.

## Lab

Library tests, on PostgreSQL 17 and 18 (seed cut, durable ack, catalog and the table above, gate, keepalive order, prepared transactions, a checkpoint behind the slot):

```bash
export CE_STREAM_PSQL=/usr/lib/postgresql/17/bin/psql CE_STREAM_PG_PORT=5432
export CE_STREAM_PG_PASSWORD=... CE_STREAM_PG_CDC_PASSWORD=...
cargo test -p ce-stream-postgres --test live -- --ignored --test-threads=1
```

The crash run: [`scripts/crash-harness/postgres/`](../../scripts/crash-harness/postgres/README.md).

Run once by hand through the CLI, with these results:

| Check | Result |
|-------|--------|
| A sink blocked 30 s against `wal_sender_timeout = 10s`, 30,000 rows | All arrive; the stream stays attached (17, 18) |
| A TOASTed value an update left alone | Filled from the old row (17, 18) |
| A `LATIN1` database | Text matches the server's own conversion to UTF-8 (17) |
| A `SQL_ASCII` database | Refused by the gate (17) |
| Generated columns | Refused, then delivered after `publish_generated_columns = stored` (18) |
| Capture from a standby, with `pg_log_standby_snapshot()` on the primary | Slot made; rows and marks delivered (17) |
| TLS: no CA; the right CA | Encrypted, per `pg_stat_ssl` (17) |
| TLS: another CA; a certificate for another host; a server without TLS | Refused (17) |

Managed services are not tested.

## Other hosts on the contract

The SQL Server and SQLite designs have no crate yet. On the contract:

- **SQL Server:** a `SeedCut` on its own connection, `mark()` from `log_end_lsn`, `wait_settled()` on `sys.dm_tran_active_transactions`, `Progress` from the tail's read position, values as [`../values.md`](../values.md) says.
- **SQLite:** no queue, since the consumer runs on the write path, and `covers` answers `Err` across a restart, since its counter does not survive one.
