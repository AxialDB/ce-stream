# Release v0.4.3 — MySQL: DDL on its own, transactions without an `Xid`

**Date:** 2026-10-11
**Tag:** [`v0.4.3`](https://github.com/AxialDB/ce-stream/releases/tag/v0.4.3)

## Summary

Fixes [#13](https://github.com/AxialDB/ce-stream/issues/13). The MySQL source delivered a transaction only at an `Xid` event. A transaction now ends where the server ends it: at its `Xid`, at its `COMMIT` query, or, for a statement that is a transaction by itself, at its one `Query` event. Mongo capture is unchanged.

## Fixed

- **A DDL statement on its own was never delivered.** `CREATE TABLE`, `ALTER TABLE`, `TRUNCATE TABLE`, `DROP TABLE`, `CREATE DATABASE`, `DROP DATABASE` and the like are written as one `Query` event with no `Xid` after it. The statement was buffered and then dropped at the next transaction. A consumer that watches `ddl` for a table being altered, truncated, or dropped never saw it.
- **Their GTIDs never entered the executed set.** `gtid_set_after` and the checkpoint had a hole at every such statement. The same held for statements that are neither DDL nor in a transaction, such as `GRANT` and `ANALYZE TABLE`.
- **Changes to a table without transactions (MyISAM) were never delivered.** Such a transaction ends with a `COMMIT` query where InnoDB has an `Xid`.
- **A DDL statement with a comment in front** (`/* ... */ ALTER TABLE ...`, as some clients send it) was not recognized as DDL.
- **`gtid_set_after` could leave out the commits just before its own.** The reader built the set from what the consumer had executed, and the consumer's set moves only when a commit is taken from the queue. While commits waited there, as they do when the source catches up after a start, the set after a commit missed them: commit 7449 arrived with `...:7431-7447:7449-7449` while 7448 was still queued. The reader now counts what it has passed on. The same holds for `gtidset` on row events. The checkpoint was never affected: it is written from the consumer's set, in order.

## What changes for a consumer

- **DDL arrives.** In `row` delivery, an `io.ce-stream.mysql.ddl` CloudEvent for each DDL statement; in `transaction` delivery, an envelope with `ddl` set and no events. Before, DDL arrived only with `CREATE TABLE ... SELECT`, the one DDL statement whose rows end with an `Xid`. A consumer that ignored DDL because it never came should look at what it does with it now.
- **More commits without events.** One for each statement that is a transaction by itself and is not DDL. They are handled like the commits whose rows the include list leaves out: the checkpoint moves, nothing else happens.
- **The executed set has no holes for these statements any more.** A checkpoint written by an earlier version keeps the holes it has; the server sends those statements once more on the next start, and they close.
- **`gtid_set_after` is the set after that commit whatever the queue holds.** A consumer that stores it as its position needs no change. One that worked around the gap by merging each set into the one it had can keep doing so; the merge now changes nothing.
- **`ddl` carries the statement as the server logged it**, with a comment in front if the client sent one.

## Not supported, as before

- XA transactions: the rows between `XA START` and `XA PREPARE` are not delivered. The stream goes on, and the `XA COMMIT` arrives as a commit without events.
- A transaction the binlog ends with `ROLLBACK`.

For both, a warning names the GTID and the number of buffered rows.

## Tests

`crates/ce-stream-mysql/tests/transaction_shapes.rs` has one test per event sequence, each taken from a MySQL 9.7.2 binlog with `mysqlbinlog`. One more feeds a run of commits that nobody takes from the queue and checks the set of each. They run in CI.
